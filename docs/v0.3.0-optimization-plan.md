## 架构瓶颈分析

### 瓶颈 #1: 写入时信息不可逆损耗 (影响 70% 失败)

**当前流程：**
```
对话 (原文) → 800token 切 chunk → LLM 提取 5-8 条记忆 (每条 50-100 token)
```
**压缩比 6-8x，细节不可逆丢失。**

关键：chunk_store 里 **已经保存了原文**（chunks.content），但 recall 时：
- assembler 只对 top-5 记忆做 source backtrack
- 每个 chunk 只取前 500 字符
- 这意味着即使原始信息存在，也没有被充分利用

**典型失败：**
```
原文: "薪资从85万涨到150万，团队从5人扩到12人"
提取: "用户获得了更好的薪资待遇" 
→ 回答问题时：数字已不可恢复（即使 chunk里有）
```

### 瓶颈 #2: 时间推理能力缺失 (影响 28% 失败)

- `temporal-reasoning` 27.2%、`temporal` 25.5% — **最差的两个类别都是时间**
- 大量记忆 `event_date = NULL`（相对日期如"上周""前几天"未锚定）
- assembler 的 `_build_temporal_reasoning` 只在检测到 duration/comparison 查询时触发
- locomo-real temporal 需要精确到"The Friday before 15 July 2023" — 需要日历计算

### 瓶颈 #3: 检索覆盖率不足 (影响 64% 失败)

- hybrid_search 默认 `top_k=20` 但最终只返回 `limit=10` 条
- 对于需要聚合多条信息的题目（如"列出所有宠物"），10条远远不够
- RRF 融合权重（vector:1.0, FTS:1.0, temporal:0.8, tag:0.5）未针对不同查询类型调优
- multi-hop 的 agent_recall 分解质量不稳定
- `min_sim=0.5` 可能太高，导致长尾信息被截断

### 瓶颈 #4: 噪声与干扰 (影响 multimodal 50%)

- mm-noise-resist 50%：系统无法区分用户项目素材 vs 朋友分享的无关内容
- 噪声过滤发生在 ingest 端 (noise_filter.py)，但不够精准
- 同 session 的噪声消息被存入记忆，recall 时混淆

## v0.3.0 优化计划

### 设计原则
1. **记忆做索引，原文做 source-of-truth** — 不依赖 LLM 提取的完美性
2. **按查询类型走不同路径** — temporal/aggregation/single-fact 用不同策略
3. **量化每个改动的影响** — 改一个跑一个，不累积风险

---

### Sprint 4: 源文回溯增强 + 检索扩量 (预期 +8~12%)

> **核心思路**：不改写入，用已有的 chunk 原文弥补提取损耗

#### 4.1 Chunk 回溯全量化 ⚡ 最高优先
**问题**：assembler 只对 top-5 记忆做 500 字符回溯，大量细节被截断

**方案** (改 `assembler.py`):
- 对 **所有** top_k 记忆做 chunk 回溯（不限 top-5）
- chunk 内容截取增加到 **1000 字符**（覆盖原始 800 token chunk 的大部分）
- 去重：同 chunk_id 只展示一次
- chunk 内容按相关性排序：命中记忆在 chunk 中的上下文前后各取 200 字

**改动范围**：`assembler.py` Lines 234-249 (backtrack section)
**改动量**：小（~30 行）

**预期影响**：
- stress-scale +15% (数值细节可从原文恢复)
- locomo multi-hop +8% (多条记忆的源文拼接更完整)
- longmemeval-s detail +6%

#### 4.2 搜索扩量 + 动态 top_k
**问题**：固定 limit=10 对聚合类查询不够

**方案** (改 `recall.py` + `hybrid_search.py`):
- query_analysis 检测到 `aggregation`/`listing`/`timeline` 意图时，dynamic `limit=20`
- hybrid_search 内部 `top_k` 从 20 提升到 **40**
- 对 multi_hop 查询：每轮搜索结果不截断，最终 RRF 融合后再截取
- assembler 的 `max_memories` 跟随 limit 动态调整

**改动范围**：
- `recall.py`: limit 参数动态化（~10 行）
- `hybrid_search.py`: top_k 提升（~5 行）
- `assembler.py`: max_memories 跟随 limit（~3 行）

**改动量**：小

**预期影响**：
- locomo multi-hop +5%
- stress-scale +8% (更多数值记忆被检索到)
- longmemeval-s multi-session +5%

#### 4.3 向量搜索阈值下调
**问题**：`min_sim=0.5` 可能过滤掉语义相关但表述不同的记忆

**方案** (改 `hybrid_search.py`):
- `min_sim` 从 0.5 下调到 **0.35**
- 依赖后续 reranker 做精排（已有 cross-encoder reranker）
- 监控：增加 recall 日志记录被过滤的候选数量

**改动范围**：`hybrid_search.py` Line 60（1 行）
**改动量**：极小

**预期影响**：
- locomo-real single-fact +5% (边缘匹配被保留)
- multimodal +3%

---

### Sprint 5: 时间推理重建 (预期 +6~10%)

> **核心思路**：让系统能做日期计算和时间线排序，而不仅是文本匹配

#### 5.1 强制时间锚定 ⚡ 最高优先
**问题**：大量记忆 event_date=NULL，时间推理无基础数据

**方案** (改 `extractor.py` + `ingest.py`):
- **Session timestamp 回填**：如果 LLM 未提取 event_date，使用 session 的 timestamp 作为近似日期
- **相对时间锚定增强**：扩展日期解析规则，支持：
  - "前几天" → session_date - 3 days
  - "上个月" → session_date month - 1
  - "去年" → session_date year - 1
  - "最近" → session_date - 7 days
  - "a few days ago" → session_date - 3 days
  - "last month" → session_date month - 1
- **Chunk 级 session_date**：ingest 时确保每个 chunk 的 metadata 中都有 session_date

**改动范围**：
- `extractor.py`: 扩展 `_fix_relative_dates()` 规则（~30 行）
- `ingest.py`: 回填 event_date 逻辑（~10 行）

**改动量**：中

**预期影响**：
- longmemeval-s temporal-reasoning +15% (从 27.2% → ~42%)
- locomo-real temporal +10% (从 25.5% → ~35%)

#### 5.2 时间推理 Always-On
**问题**：`_build_temporal_reasoning` 只在检测到 duration/comparison 关键词时触发

**方案** (改 `assembler.py`):
- **Always-On 模式**：只要有 ≥2 条带 event_date 的记忆就生成时间排序
- **时间线综述**：自动生成 "时间线：[最早日期] ~ [最晚日期]，共 N 个事件"
- **日期差计算增强**：支持月差、年差、工作日差

**改动范围**：`assembler.py` Lines 322-410（~20 行改动）
**改动量**：小

**预期影响**：
- temporal-reasoning 全面覆盖 +3%
- locomo temporal +5%

#### 5.3 Temporal-First 检索路径
**问题**：时间类查询走向量搜索，结果不一定是时间相关的

**方案** (改 `recall.py` + `hybrid_search.py`):
- 当 query_analysis 检测到 temporal intent 时：
  - **RRF 权重调整**：temporal path 权重从 0.8 提升到 **1.5**
  - **日期范围搜索优先**：如果能从查询中提取日期/时间段，先走 SQL date range 查询
  - **Session 范围搜索**：对 "session X 讨论了什么" 类查询，直接查 chunk_store by session

**改动范围**：
- `recall.py`: temporal 路径权重调整（~15 行）
- `hybrid_search.py`: RRF 权重参数化（~10 行）

**改动量**：中

**预期影响**：
- locomo-real temporal +8%
- longmemeval-s temporal-reasoning +5%

### Sprint 6: 聚合推理 + 噪声抵抗 (预期 +4~8%)

#### 6.1 数值聚合专用路径
**问题**：stress-scale 需要 "天猫2100万+京东1050万=5300万" 级别的精确聚合

**方案** (改 `recall.py` + `assembler.py`):
- query_analysis 检测到数值聚合意图 (金额/数量/统计) 时：
  - `limit` 提升到 **30**
  - 强制 chunk 回溯：对所有命中记忆回溯源文，提取数值
  - assembler 新增 `## 数值汇总` section：自动从 chunk 原文提取所有数字及上下文
- 数值提取规则：正则匹配 `\d+[万亿k千百%元]` 模式，保留前后 50 字上下文

**改动范围**：
- `recall.py`: 数值路径（~20 行）
- `assembler.py`: 数值汇总 section（~40 行）

**改动量**：中

**预期影响**：
- stress-scale 10k +15% (从 56% → ~71%)
- stress-scale 50k +10% (从 31% → ~41%)
- stress-scale 100k +8%

#### 6.2 噪声源标记
**问题**：multimodal noise-resist 50%，无法区分用户素材 vs 朋友分享

**方案** (改 `ingest.py` + `noise_filter.py`):
- ingest 时为每条记忆标记 **conversation_role**：
  - "user_stated": 用户明确说的
  - "shared_by_other": "朋友发来""同事分享""看到一个" 类模式
  - "assistant_advice": 助手回应的
- recall 时：对 noise-resist 类查询（"A和B有关系吗？"），优先返回 user_stated 记忆
- assembler 标注来源：`[用户提到]` vs `[他人分享]`

**改动范围**：
- `ingest.py`: 角色标记（~20 行）
- `noise_filter.py`: 标记规则（~30 行）
- `assembler.py`: 来源标注（~10 行）

**改动量**：中

**预期影响**：
- multimodal mm-noise-resist +15% (从 50% → ~65%)
- multimodal mm-cross-ref +5%

#### 6.3 知识过期检测增强
**问题**：conflict-resolution expired-info 44%，旧信息覆盖新信息

**方案** (改 `conflict.py` + `recall.py`):
- conflict detect 时：如果新记忆和旧记忆涉及同一实体同一属性 (如"工作""地址""饮食")，且新记忆有更近的 event_date → 自动 supersede
- recall 时：若 superseded_by 不为空，跳过旧记忆（当前已有此逻辑，检查是否生效）
- assembler 中标注 "⚠ 已过期" 提醒

**改动范围**：
- `conflict.py`: 时间感知 supersede（~25 行）
- `recall.py`: 检查过期逻辑（~5 行）

**改动量**：中

**预期影响**：
- conflict-resolution expired-info +15% (从 44% → ~59%)
- longmemeval-s knowledge-update +8%

| 编号 | 任务 | 改动文件 | 改动量 | 预期提升 |

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| Chunk 回溯增加 context 过长 | LLM judge 超 token limit | 控制总 context ≤ 4000 token |
| top_k 扩大导致延迟增加 | 搜索慢 3-5x | 只对特定查询类型扩量 |
| min_sim 下调引入噪声 | 精度下降 | 依赖 reranker 精排 |
| 时间锚定不准确 | 错误日期比空更有害 | 标记为 "approximate_date" |
| 数值聚合正则误匹配 | 无关数字进入汇总 | 限定上下文语境 |
